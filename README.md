I did not use `<article>` or `<aside>`, since none of my content represented a self-contained, independently distributable piece of content (which `<article>` is meant for), nor did I have supplementary sidebar-style content that would justify `<aside>`. Instead of `<article>`, I used a generic `.project-card` and `.timeline-item` (a `<div>`) for each project/experience entry, since these blocks are only meaningful within the context of their parent section rather than being reusable as standalone content. Using semantic tags like `<section>` and `<header>` still helped in two concrete ways: it made the document outline easier to read and navigate (both for me while editing and for assistive technologies like screen readers), and it gave me natural anchor points (`id="profile"`, etc.) to hook into for the in-page navigation links.

2. The biggest responsive challenge was the hero section, which uses a two-column CSS Grid (`grid-template-areas: "identity photo" "details photo"`) to place the profile photo beside the text on desktop. On smaller screens, keeping this three-part layout side-by-side made the photo too small and the text cramped. I evaluated which elements to reprioritize by asking: which content answers "who is this person" first? The name and role (identity) needed to stay at the top, the photo needed to be visually prominent but not push the bio text too far down, and the bio/meta details were the least urgent so they could be moved to the bottom. I solved this with a `max-width: 600px` media query that redefines `grid-template-areas` to a single column stacked as `"identity" "photo" "details"`, and capped `.hero-photo` to `max-width: 220px` so the photo doesn't dominate the screen on mobile. I also switched `.social-links` to wrap and align left instead of matching the desktop layout, since horizontal buttons don't scale well on narrow viewports.

3. Since the site is purely static, all content (skills, experience entries, project descriptions) is hardcoded directly into the HTML. This means every time I want to add a new skill, project, or organizational experience, I have to manually edit the HTML file, which does not scale well and increases the risk of inconsistent formatting between entries. There's also no way for a visitor to interact with the content beyond reading it — there's no contact form that actually sends a message, no way to filter or search through projects, and no persistent way to track something like page visits. Based on these limitations, the dynamic functionality I'd most want to add next is a backend (using Django) with a database-backed model for skills, experience, and projects, paired with an admin interface so I can add or edit entries without touching raw HTML. A working contact form that actually delivers messages (instead of just a `mailto:` link) would also be a natural next step, since it's the most immediately useful missing interactive feature for a portfolio site.

### Assignment 2

1. When a user opens a new portfolio page (for example, the Projects page), the request flow starts at the project-level `urls.py` (e.g. `portofolio/urls.py`), which acts as the entry point for all incoming URLs. This file typically includes the application's URL configuration using `include()`, forwarding any unmatched path to the app-level `main/urls.py`. Inside `main/urls.py`, the specific path (in this case `projects-page/`) is matched against a registered `path()` entry, which maps that URL to a corresponding view function, `show_projects_page`. The view then queries the database through the `ProjectItem` model using `ProjectItem.objects.all()`, retrieving every stored project as a QuerySet. This QuerySet is placed into a context dictionary along with any other data the template needs (such as the site name), and passed into `render()` together with the target template file, `projects_page.html`. Inside the template, Django Template Language processes the `{% for project in project_list %}` loop, rendering one card per project object and pulling out each field (title, subtitle, description, image) using dot notation. Once rendering is complete, Django returns the finished HTML as an HTTP response, which the browser then parses and displays to the user.

2. Storing portfolio data in a model rather than hardcoding it directly into the template keeps the application's content and structure cleanly separated, which has a direct impact on maintainability. If project data were hardcoded in HTML, every new project, edit, or removal would require manually editing the template file and redeploying the application, increasing the risk of introducing typos or breaking the page's structure. By storing data in a model instead, content can be added, edited, or removed through the Django Admin interface or shell without touching any HTML at all, and the same underlying data can be reused across multiple templates or exposed through a future API if needed. This separation also allows the data to benefit from Django's built-in validation, querying, and filtering capabilities (for example, being able to sort projects by date or filter by category), none of which would be possible if the information were simply written as static text inside a template file.

3. `makemigrations` inspects the current state of the models defined in `models.py`, compares it against the migration history, and generates a new migration file describing the changes needed to bring the database schema up to date with the models — but it does not touch the actual database. `migrate`, on the other hand, takes the migration files that already exist (including the one just generated) and actually applies those changes to the database, creating or altering tables and columns as instructed. A concrete example from this assignment: after adding the `image_url` and `link_url` fields to the new `ProjectItem` model, I ran `python manage.py makemigrations` to generate a migration file describing the addition of these two new columns, and then ran `python manage.py migrate` to actually apply that migration and create the corresponding columns in the SQLite database.
