When a user opens a new portfolio page (for example, the Projects page), the request flow starts at the project-level `urls.py` (e.g. `portofolio/urls.py`), which acts as the entry point for all incoming URLs. This file typically includes the application's URL configuration using `include()`, forwarding any unmatched path to the app-level `main/urls.py`. Inside `main/urls.py`, the specific path (in this case `projects-page/`) is matched against a registered `path()` entry, which maps that URL to a corresponding view function, `show_projects_page`. The view then queries the database through the `ProjectItem` model using `ProjectItem.objects.all()`, retrieving every stored project as a QuerySet. This QuerySet is placed into a context dictionary along with any other data the template needs (such as the site name), and passed into `render()` together with the target template file, `projects_page.html`. Inside the template, Django Template Language processes the `{% for project in project_list %}` loop, rendering one card per project object and pulling out each field (title, subtitle, description, image) using dot notation. Once rendering is complete, Django returns the finished HTML as an HTTP response, which the browser then parses and displays to the user.

2. Storing portfolio data in a model rather than hardcoding it directly into the template keeps the application's content and structure cleanly separated, which has a direct impact on maintainability. If project data were hardcoded in HTML, every new project, edit, or removal would require manually editing the template file and redeploying the application, increasing the risk of introducing typos or breaking the page's structure. By storing data in a model instead, content can be added, edited, or removed through the Django Admin interface or shell without touching any HTML at all, and the same underlying data can be reused across multiple templates or exposed through a future API if needed. This separation also allows the data to benefit from Django's built-in validation, querying, and filtering capabilities (for example, being able to sort projects by date or filter by category), none of which would be possible if the information were simply written as static text inside a template file.

3. `makemigrations` inspects the current state of the models defined in `models.py`, compares it against the migration history, and generates a new migration file describing the changes needed to bring the database schema up to date with the models — but it does not touch the actual database. `migrate`, on the other hand, takes the migration files that already exist (including the one just generated) and actually applies those changes to the database, creating or altering tables and columns as instructed. A concrete example from this assignment: after adding the `image_url` and `link_url` fields to the new `ProjectItem` model, I ran `python manage.py makemigrations` to generate a migration file describing the addition of these two new columns, and then ran `python manage.py migrate` to actually apply that migration and create the corresponding columns in the SQLite database.

### Assignment 3
1. We use Django's `ModelForm` instead of writing HTML forms manually because it automatically generates form fields directly from the model's field definitions, inheriting their data types, validators, and constraints (e.g., `max_length`, required fields, choices). This removes duplication — we don't have to redefine the same rules twice, once in `models.py` and once in raw HTML — and Django validates the submitted data against those rules before saving. `ModelForm` also provides `.save()`, which converts validated input directly into a model instance and writes it to the database, instead of us manually reading `request.POST`, converting types, and constructing the object ourselves. This makes the code shorter, less error-prone, and easier to keep in sync with the model.
    We add `{% csrf_token %}` to every POST form because Django protects against Cross-Site Request Forgery (CSRF) attacks, where a malicious website could trick a logged-in user's browser into submitting an unwanted POST request to our site (using the user's own session cookies). The `{% csrf_token %}` tag inserts a unique, secret token into the form; when the form is submitted, Django checks that this token matches the one it issued. Since an attacker's site cannot know or guess this token, forged requests are rejected. Without it, Django's CSRF middleware blocks the POST request with a 403 error.

2. JSON is generally preferred because it is less verbose than XML (no opening/closing tags for every element), which results in smaller payloads and faster network transfer. It is also native to JavaScript — since JSON syntax mirrors JavaScript object literals, browsers can parse it directly with `JSON.parse()` without any extra library, while XML requires separate DOM-parsing tools. JSON is simpler to read and write, doesn't require a schema (like XSD/DTD) to be understood, and parses faster due to its simpler structure. These traits make it a better fit for REST APIs and modern web/mobile applications, where data is frequently exchanged between the server and JavaScript-based clients.

3. The flow is: (1) a request hits a view function such as `get_experiences_json`; (2) the view queries the database using the ORM (e.g., `Experience.objects.all()`), which returns a `QuerySet` of Python model instances; (3) these model instances are converted into a JSON string using `serializers.serialize("json", experiences)`; (4) the resulting JSON string is returned as an `HttpResponse` with `content_type="application/json"`, so the client knows how to interpret the body.

Serialization is required because Django model instances are Python objects living in memory, containing types (UUIDs, `DateTimeField`, foreign key relations, methods) that have no meaning outside of Python and cannot be transmitted over HTTP as-is. HTTP only carries bytes/text, so before the data can be sent to a browser, mobile app, or any other client — regardless of what programming language it uses — it must be converted ("serialized") into a universal, text-based format like JSON. On the receiving end, that JSON can then be parsed (or, as in `show_experience`, deserialized back into Python objects) to reconstruct usable data.
